Use Graphify first, with small context budgets (1000-3000 tokens); compare its indexed commit to current main and verify relevant current source ranges. Read README, docs/PRODUCT_REVIEW.md (owner feedback and acceptance criteria), and docs/STATUS.md. Never repeatedly fetch embedded artwork or archived HTML. Dynamic overrides and shared globals mean graph edges may be incomplete; verify the last assignment and relevant callers. GitHub main is authoritative. Preserve concurrent changes. Record test evidence and blockers in docs/STATUS.md, and concise durable Graphify notes when useful.

- Mobile first, desktop supported; four native portrait maps, not cropped landscape backgrounds. Mature Japanese watercolor illustration, no emoji props or detached limbs.
- Shrine entry every visit. First visit: railway ticket, name, character selection, journey. Preserve saved character and directional walking; approach and enter buildings naturally. Four primary dock destinations only: Explore (map, passport and travel memories), Today (tasks, luck and gratitude), Town Hall (community), My Room (home and collections). Profile/XP and Paw Coins in HUD; settings in profile.

- Living animated rooms, no generic modal or flat minigame panel. Physical tarot deal/flip, incense/bow/fortune sticks/moon blocks, strength-based koi throws with landing animation, realistic cooking/drinks, arcade, NPC encounters and persistent collectibles.
- Community noticeboard must eventually support genuine shared posts; distinguish local storage from shared data. Personality tests for fun; reflective fortune readings, not predictions.
- Prioritize verified bugs then unfinished work; preserve artwork and save keys. Test new/returning entry, languages, all doors, touch/mouse, activities, collection and save/reload on small and tall mobile, tablet and desktop. Review screenshots. Never claim passes or deployment without evidence.
- Edit readable src files, not encoded legacy chunks. Run node scripts/build.cjs and browser tests. Batch related improvements into coherent commits and update status. Automated test success is not visual acceptance.

## Non-negotiable art quality (owner, 26 November)
- Visible character, prop, furniture, collectible, result card, game cabinet and activity art must be individually illustrated, with a coherent nostalgic Japanese watercolor/gouache art direction. Simple procedural vector shapes, flat recolors, generic icon packs and geometric substitutes are temporary fallback art only, never a finished deliverable.
- Rooms may be intentionally sparse, but their lighting, architecture, materials and foreground/background composition still need to feel like the same painted world. Do not fill every empty area with decoration.
- Draw actual character poses, tool contact, feet pivots, seating and coherent shadows. Do not disguise missing animation with boxes or floating objects. Keep character size appropriate to each room and camera.
- Prioritize final raster assets, original painted portrait/landscape compositions and isolated transparent sprites, with documented anchors and load budgets; reuse existing illustrated assets when suitable. Code remains responsible for motion, hit areas, accessibility and responsive layout.
- Before accepting an activity, inspect actual mobile and desktop screenshots and an exported share image where applicable. Review art quality, composition, readability, character proportions and prop contact. Passing code tests never constitutes visual approval. Work in coherent batches of up to 20 related improvements when requested; record actual evidence and explicitly flag interim art.


## Hard release rule (owner, 27 November 2026)
The developer is responsible for end-user quality, not the owner acting as first tester. Apply this to every district, room, inner activity, entrance, journey, dock tab, nested page, result and empty/loading state. Before marking any item complete:
1. Read current GitHub main and effective runtime overrides; reconcile the latest owner screenshots and all prior feedback with what actually loads in the game. Do not infer completion from a commit message, concept board or stale indexed code.
2. Design the full player journey (entry, discover, approach, interact, meaningful response, finish, return, revisit). Review as game designer, art director, animator, UI/UX designer, mobile and accessibility tester, localization reviewer and engineer, including layout, scale, depth, timing, contact, sound, content and replayability.
3. Implement in the actual game. No duplicate painted and vector props, floating icons/tools, oversized objects, characters on furniture, NPC or dialogue obscuring actionable signage, clipped text or horizontal scrolling. Use coherent painted assets and physically registered controls. Fallbacks are not final artwork.
4. Play the entire journey through actual rendered browser input, not only direct state injection. Inspect screenshots/animation at important stages in both languages and mobile/desktop sizes; check fresh/returning visits, interruption, exit, persistence and repeat. Test regressions across affected screens. Verify the actual deployed revision before handing it over.
5. Fix every discovered defect and repeat the playthrough. Record commit, build/CI, observed screenshots and playback evidence, and any unresolved blocker. A code assertion, syntax check or successful deployment is not player-experience acceptance. Mark unverified or interim work as incomplete. Do not hand known defective work to the owner as finished. Do not advance acceptance counts on code-only changes.
Prioritize coherent, polished vertical slices over counting batches or creating additional breadth; all four redesigned maps and all inner interfaces remain open until independently rendered and reviewed.

## Manual and hourly development coordination (owner, 27 November 2026)

The scheduled Pawradise Development automation remains enabled every hour at minute 11 (Asia/Singapore). Do not restart completed work or trust historical counts in a chat or automation prompt.

- Before each write, refresh the current branch head and relevant file blob SHAs; inspect changes made since the session began. Prefer independent workstreams when overlap is detected. Use guarded writes, preserve other contributors' changes, and on a conflict refresh/reconcile or change workstream. Never force push or silently overwrite concurrent edits. These checks mitigate conflicts but do not constitute an exclusive workstream lock.
- After each substantial batch, record stable task ID, player-facing outcome, commit, automated test results, actual mobile/desktop visual evidence, remaining defects and next actionable task in the durable checkpoint. Separate implemented, automatically tested, deployed and visually accepted states. Update status when relevant. Do not count plans or duplicate changes as gameplay completion.
- The next runner resumes from the newest committed checkpoint and reconciles it with newer source commits before editing. Do not ask the owner to repeat instructions. Do not pause the hourly automation unless the owner asks or all outstanding development has been verified complete under the hard release gate.

Give asset production, code and verification independent tasks wherever practical.

1. Refresh current main and register blob SHA. Use Graphify for narrow dependency discovery when useful; always prefer newer GitHub source. Select an available task whose dependencies are at least tested. A task lease is exclusive across all listed resources (including shared source files and browser access). Use a distinct runner ID and current UTC epoch milliseconds. Use scripts/workstream-registry.cjs mutate/eligible functions, or the same validated algorithm in the connector, to claim an available task. Commit the claimed registry with the exact fetched blob SHA before starting; on a conflict fetch again and choose a new available task. Do not assume distinct task IDs imply independent file writes.
2. Lease default 30 minutes, renewable while working (1–60 minute bounds). Recheck ownership immediately before every write; do not write after expiry or loss of ownership. Expired claims can be reclaimed only after checking recent commits and actual progress. If an active runner owns a shared file or browser resource, use another available independent task rather than duplicate or wait. Do not create multiple automation schedules or evade usage limits. Actual concurrency is subject to available sessions and tools.
3. Work in coherent batches: recover/create necessary art, implement, integrate, run relevant tests, inspect rendered results, fix and retest. Preserve the curated product and mandatory release gates. Use a guarded GitHub multi-file commit when supported, otherwise guarded file updates, and verify the resulting commits. Record test artifacts and evidence. After each substantial batch update the checkpoint and release the registry claim with current stage, commit/test evidence, and exact blockers. Renew long-running claims before expiry; if blocked release promptly and pick another eligible task. Never mark visual acceptance on syntax or helper assertions alone. Stages are outstanding, implemented, tested, visually_verified, accepted. Art-only staging is not final gameplay acceptance.
4. Use narrow current-source reads and reusable test commands instead of repeatedly loading all source. Work from exact current head; if Graphify is stale, only use it as a navigation aid. Commit tested work and its durable evidence before moving to the next task. Ten substantial batches per segment remains a target when scope and limits permit, not a count to inflate. The hourly cadence remains unchanged.

Registry helper verification: `node scripts/workstream-registry.cjs --self-test`. The helper produces a proposed registry mutation; it does not acquire a remote lease itself. A successful expected-blob-SHA GitHub write is required to acquire or release it. If using the CLI, persist only the returned registry object, not the wrapper. ## Continuous completion policy (owner, 27 November 2026)

Every manual "continue", "resume" or "proceed" authorizes actual development aimed at completing as many outstanding workstream deliverables as the current session permits, not merely touching or advancing tasks. This supersedes the earlier three-workstream target; there is no fixed batch cap. Begin with the latest registry, checkpoint, owner feedback and active resource leases. Prioritize release-critical items and near-complete deliverables that can genuinely be finished with available tools. For each selected workstream, resolve its remaining actionable acceptance requirements, implement or integrate the missing pieces, verify the complete deliverable, commit and record evidence before switching to the next. An existing implementation that genuinely satisfies its full workstream scope should be verified rather than unnecessarily rewritten.

A workstream counts as cleared from outstanding implementation only after all its required implementation is complete and evidence supports a legitimate stage transition to implemented or tested. A partial change, code syntax check, regression helper, planning update, or lease release alone does not clear a workstream. Report stage counts honestly; implementation clearance is distinct from visual verification and final product acceptance. Never move a visual-only or deployment-only workstream out of outstanding just because its code parses. Keep visual, live service, artwork and actual end-user acceptance gates intact.

Automatically begin the next eligible workstream after each completion; do not voluntarily stop at three workstreams or any arbitrary batch size. If a task is genuinely blocked by missing artwork, a service, browser access, a dependency or an active lease, record the specific blocker, preserve partial work, release the lease and choose a different eligible workstream that can be finished. Do not invent additional scope, split existing tasks to inflate the count, or postpone required fixes by calling them optional. Maintain one canonical registry and distinguish remaining implementation from remaining release verification. Continue actual implementation and verification until every actionable outstanding item is complete or an actual session/tool limit is reached. Commit and checkpoint each completed deliverable so the next manual continue resumes without losing work. If any items remain, report the actual number cleared, remaining count and specific blockers. Do not wait for confirmation between batches. Keep checkpoint updates concise. Preserve the existing hourly automation schedule and coordinate through leases; all source changes must remain guarded against concurrent edits.
