## Stable release lane and parallel branch rule (owner, 28 November 2026)

This rule supersedes earlier instructions to make claim, checkpoint or implementation commits directly to main. Frequent main pushes have caused pending browser jobs and GitHub Pages deployments to be replaced before they can run. The objective is continued parallel implementation with a stable release candidate, not a pause in development.

1. Treat main as the integration and live deployment lane. Every development session, manual or scheduled, first reads main, current Actions runs, open PRs and active scopes. Develop on unique branches, with draft PRs or branch-local checkpoints declaring the canonical workstream ID and file scope. Avoid intersecting open claims. Do not commit task claims, lease renewals, audit notes or progress-only updates to main. The hourly automation must never push or merge into main.
2. Keep related implementation, tests and status/evidence in coherent branch commits. Continue other independent work on separate branches while main tests or deployment are active. Preserve the canonical workstream register on main; branch-local claims do not imply completion or exclusive main registry ownership. The release coordinator reconciles actual scope and stage against the latest registry at integration, without overwriting concurrent records.
3. Only one interactive release coordinator may integrate a candidate to main at a time. Before integration, inspect the latest main head and relevant Pages, browser, organic journey, entrance and railway runs for the last code-bearing release SHA. If relevant jobs are queued, pending or running, do not push another main commit; continue branch development instead. If runs fail or are cancelled, identify the actual blocker, prepare a coherent corrective candidate, and allow one guarded corrective integration when the previous jobs are terminal. Do not treat cancellation as success. Combine compatible reviewed branches and register updates into a single release commit where practical. Use expected-head guarded ref updates or a fresh reviewed merge; never force-push or merge stale changes.
4. After integration, record the exact main SHA and run links on a branch or in the session, and leave main unchanged until the relevant checks and Pages deployment for that revision finish. Do not create a separate main commit merely to record the SHA. Record verification in the next coherent release. A successful older deployment does not prove the latest revision is live. Keep completed, staged, tested, deployed and visually accepted states distinct.
5. This is a cooperative release gate, not a substitute for branch protection. Keep hourly automation enabled, work through unclaimed deliverables, and do not ask the owner to repeat this rule. Report branch/PR evidence and exact release blockers; do not silently bypass the gate.
